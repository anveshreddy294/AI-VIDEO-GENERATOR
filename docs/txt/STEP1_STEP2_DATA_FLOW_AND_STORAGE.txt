2. STEP 1: MULTIMODAL INGESTION PIPELINE (DATA FLOW & STORAGE)
================================================================================

Endpoint: POST /upload (with optional ?auto_start_assessment=true)
File: app/api/upload.py

2.1 STAGE 1: RECEPTION & REGISTRATION
--------------------------------------
1. The user uploads a file through POST /upload or the Web Dashboard.
2. File is written temporarily to disk:
   Path: storage/uploads/<uuid>_<filename>
3. File Validation & Registration (app/services/registry.py::register_source):
   - Validates file extension and magic byte signatures (PDF, PNG, JPG, MP4, MOV, MKV, TXT).
   - Enforces file size limit (<500MB).
   - Computes SHA-256 file checksum to detect duplicates.
   - Assigns unique deterministic identifiers:
     * source_id: e.g. "SRC_63d54087dc2e"
     * asset_id:  e.g. "AST_c9e1b20e3a93"
     * upload_id: e.g. "UPL_239d8275fb21"
   - If SHA-256 exists in registry:
     Increments "version" (e.g. version 2) and records parent_source_id.
   - Original file is copied to permanent storage:
     Path: storage/uploads/{source_id}/original.<ext>
   - Source record is written to master registry index:
     Path: storage/registry/sources_index.json
   - Status updated: UPLOADED -> PROCESSING -> EXTRACTING

2.2 STAGE 2: MODALITY DISPATCHING & NORMALIZATION
-------------------------------------------------
File: app/services/dispatcher.py::dispatch
1. Router inspects MIME type / extension and dispatches to specific modality extractor:
   - PDF (app/services/extractor.py): Uses PyMuPDF (fitz) to extract text blocks, line numbers,
     bounding boxes, and page numbers. Renders embedded images and invokes Gemini Vision.
   - Text (app/services/dispatcher.py): Normalizes whitespace and splits by semantic paragraphs.
   - Image (app/services/vision.py): Uses Gemini Vision API to describe diagrams, flowcharts,
     or textual figures into dense semantic transcriptions.
   - Video (app/services/video/pipeline.py): 4-Phase video matrix:
     * Phase 1 (av_splitter.py): FFmpeg 16kHz mono WAV extraction.
     * Phase 2 (transcriber.py): faster-whisper ASR transcription with word/segment timestamps.
     * Phase 3 (frame_extractor.py): OpenCV keyframe extraction with 32x32 grayscale perceptual
       deduplication (<4% change skipped) + Gemini Vision description.
     * Phase 4 (fusion.py): Multimodal temporal fusion merging speech and visual descriptions
       into unified ContentUnits within 2.0s jitter tolerance.
2. Normalization:
   Every extraction produces a uniform list of ContentUnit objects:
   - content_id: e.g. "CU_d8ec3544007b"
   - source_id: "SRC_63d54087dc2e"
   - text: Raw extracted text or visual description
   - page_number: (for PDFs)
   - timestamp_start / timestamp_end: (for Videos)
   - sequence_index: Ordering in document
   - bbox: Bounding box coordinates [x0, y0, x1, y1]
3. ContentUnits are saved to disk:
   Path: storage/registry/<source_id>/content_units.json

2.3 STAGE 3: STRUCTURE DETECTION, CONCEPT EXTRACTION & KNOWLEDGE GRAPH
----------------------------------------------------------------------
File: app/services/structurer.py::process_structure_and_concepts
Status: NORMALIZING
1. ContentUnits are analyzed using Gemini (gemini-3.5-flash) or grounded heuristic fallback:
   - Detects structural hierarchy (Chapters and Sections).
   - Extracts discrete concepts taught in the text.
   - Identifies prerequisite concept relationships (DAG structure).
2. Construct KnowledgeGraph schema:
   Concepts dictionary:
   {
     "CONCEPT_COARSE_ALIGNMENT": {
       "concept_id": "CONCEPT_COARSE_ALIGNMENT",
       "name": "Coarse Alignment",
       "definition": "Initial stage where transmitter locates remote terminal within camera FOV.",
       "prerequisite_concept_ids": ["CONCEPT_FSOC"],
       "related_concept_ids": [],
       "source_content_ids": ["CU_d8ec3544007b", "CU_77ceae05d22d"]
     }
   }
3. Fallback Heuristic Resiliency:
   If Gemini API hits rate limits (HTTP 429 quota exhaustion), the structurer switches
   instantly to grounded rule-based extraction, parsing headings, capitalized acronyms,
   and definitions directly from ContentUnits so concepts are NEVER empty.
4. Derives TopicBlueprint:
   - topic_name: e.g. "Free Space Optical Communication"
   - key_concepts: List of concept names
   - prerequisites: Flattened prerequisite IDs
   - difficulty_level: "beginner" | "intermediate" | "advanced"
5. Stored to disk:
   Path: storage/registry/<source_id>/knowledge_graph.json

2.4 STAGE 4: SEMANTIC CHUNKING & VECTOR STORE SYNC (LAYER A)
------------------------------------------------------------
File: app/services/chunker.py & app/db/vector_store.py
Status: INDEXING
1. Concept-Aware Semantic Chunking:
   - Groups adjacent ContentUnits by concept boundaries and token limits (~500 tokens).
   - Produces RichChunk objects:
     * chunk_id: e.g. "CHUNK_f6366421aaae"
     * source_id: "SRC_63d54087dc2e"
     * text: Aggregated chunk content
     * layer: "A" (foundational document text)
     * concept_ids: Concepts mapped to this text chunk
     * content_ids: ContentUnits forming this chunk
     * page_start / page_end: Precise page provenance
2. Vector Store Ingestion (Layer A):
   - Dense embeddings computed via models/gemini-embedding-2 (768 dimensions).
   - Stored in Qdrant collection: visualai_layer_a (cosine distance).
   - Deterministic point ID: uuid5(NAMESPACE_DNS, f"{source_id}::{chunk_id}::{text[:100]}").
   - Guarantees idempotent upserting without duplicate points.

2.5 STAGE 5: QUALITY VALIDATION GATEWAY CHECK
---------------------------------------------
File: app/services/validator.py::validate_ingestion_quality
Status: VALIDATING -> READY
1. Tier 1 (File Gateway): Validates file size > 0, registered path exists, checksum matches.
2. Tier 2 (Content Gateway): Validates total ContentUnits >= 1, non-empty text, valid sequence order.
3. Tier 3 (Chunk Gateway): Validates RichChunks >= 1, token bounds within limits, valid source_ids.
4. Tier 4 (Concept Gateway): Validates KnowledgeGraph has >= 1 concept, DAG has no cyclical self-references.
5. Tier 5 (Storage Gateway): Verifies Qdrant points count increased, metadata payloads verified.
6. When all 5 tiers pass, source status is marked "READY" in storage/registry/sources_index.json.

Files: app/api/assessment.py, app/services/assessment/

4.1 STAGE 1: SESSION INITIALIZATION & KG SNAPSHOTTING
-----------------------------------------------------
1. Client requests assessment start via POST /assessment/start.
2. Validates that source_id exists and status == "READY".
3. Creates unique session_id: SESS_<uuid4_hex>.
4. KG Snapshotting (ConceptSnapshot):
   Extracts compact concept records (concept_id, name, definition, prerequisites, difficulty)
   and embeds them directly into the AssessmentSession object.
   Benefit: Decouples the active quiz from external disk modifications during testing.
5. Initializes AssessmentSession:
   Path: storage/assessment_sessions/<session_id>.json
   Status: PLANNING

4.2 STAGE 2: DYNAMIC ASSESSMENT PLANNING & RESERVE POOL
-------------------------------------------------------
File: app/services/assessment/planner.py::plan_assessment
1. Concept Selection Strategy:
   - Cold Start: Distributes target question count across difficulty levels:
     * ~30% Foundational (Beginner)
     * ~40% Intermediate
     * ~30% Advanced
   - Prerequisite Pairing: If an advanced concept is tested, its prerequisite parent
     is automatically paired into the quiz candidates to enable diagnostic gap detection.
   - Profile-Driven (Adaptive): If student profile already exists, prioritizes unmastered
     concepts (status == LEARNING) and avoids mastered concepts.
2. Candidate Planning:
   - Selects primary concept candidates matching max_questions.
   - Selects reserve candidate concepts to form a backup pool in case primary candidates
     fail validation gateways.

4.3 STAGE 3: SOURCE-ISOLATED GROUNDED QUESTION GENERATION
---------------------------------------------------------
File: app/services/assessment/generator.py::generate_question_for_concept
1. Source-Isolated Retrieval:
   - Queries Qdrant collection visualai_layer_a with concept name and definition.
   - STRICT FILTER: Must match payload { "source_id": source_id, "layer": "A" }.
   - Prevents cross-document data leakage between different textbooks/courses.
2. Grounded LLM Prompting:
   - Pluggable LLM Provider (GeminiProvider, OllamaProvider, or deterministic MockProvider).
   - Provides retrieved source text chunks as authoritative ground truth.
   - Instructs LLM to formulate a 4-option multiple-choice question (MCQ) with 1 unambiguously
     correct option, 3 plausible distractors, and an educational explanation.
3. Fallback Question Generator:
   - If LLM is unreachable or quota exhausted, uses deterministic grounded templating
     derived directly from the concept definition and source text.
   - Varied answer index hashing ensures correct answer is not always index 0.

4.4 STAGE 4: VALIDATION GATEWAYS & RESERVE BACKFILLING
------------------------------------------------------
File: app/services/assessment/validator.py::validate_question
Every candidate question must pass 3 validation gateways:
1. Structural Gateway:
   - Exactly 4 non-empty options.
   - correct_index in range [0, 3].
   - Non-empty stem, concept_id, and explanation.
2. Grounding Vocabulary Gateway:
   - Stem and options must share significant keyword token overlap with source chunks (>10%).
   - Prevents generic hallucinated questions unrelated to the study material.
3. Non-Duplication Gateway:
   - Jaccard similarity between question stems must be < 0.6.
   - Prevents repeating the same question wording twice in one session.
4. Candidate Reserve Backfilling:
   - If a primary candidate question fails any gateway, the engine pulls from the reserve
     candidate pool and generates replacement questions until target count is satisfied.

4.5 STAGE 5: SANITIZED QUIZ DISPATCH & SESSION PERSISTENCE
----------------------------------------------------------
File: app/api/assessment.py & app/services/assessment/session_store.py
1. Complete Question objects (including correct_index, explanation, source chunks)
   are written to disk:
   Path: storage/assessment_sessions/<session_id>.json
   Status: READY
2. Sanitization (SafeQuestion):
   - Hidden fields (correct_index, explanation) are stripped from the response payload.
   - SafeQuestion retains: question_id, concept_id, concept_name, stem, options, difficulty,
     variant_type, page_start, page_end, chunk_ids.
3. HTTP 200 returned to client with session_id and list of SafeQuestions.

4.6 STAGE 6: SUBMISSION GRADING, FALSE-MASTERY & KILL SWITCH ENGINE
-------------------------------------------------------------------
Endpoint: POST /assessment/submit
File: app/api/assessment.py::submit_assessment & app/services/assessment/engine.py
1. Session Integrity Validation:
   - Checks session expiration (TTL = 24 hours).
   - Validates that submitted question_ids belong to the session.
   - Rejects duplicate question submissions.
2. Scoring:
   - Compares student's selected_index against ground-truth correct_index.
   - Computes concept scores and overall quiz score percentage.
3. Prerequisite Gap Detection:
   - Identifies conceptual dependency failures:
     * Failed child concept AND failed parent prerequisite.
     * Failed child concept while parent prerequisite was unmastered.
4. False-Mastery Safeguard:
   - Requires consecutive correct threshold (mastery_threshold = 2)
     before transitioning a concept to "MASTERED".
   - Single lucky guesses remain "LEARNING".
5. Anti-Loop Kill Switch:
   - Tracks consecutive failure iterations per concept.
   - If iteration_count > kill_switch_limit (default 3):
     Concept status is marked "REQUIRES_HUMAN_FALLBACK".
   - These concepts are permanently excluded from automated video loops and flagged
     for human instructor intervention.
6. Updates StudentLearningProfile:
   - Persists strong_concepts, weak_concepts, concept_ids, and scores.
   - Saved to Disk:
     Path: storage/learning_profiles/<student_id>_<source_id>.json

4.7 STAGE 7: VIDEO TARGET MATRIX HANDOFF GENERATION
---------------------------------------------------
File: app/services/assessment/video_target.py::build_video_target_matrix
1. Evaluates all assessed concepts:
   - Mastered concepts (score >= 70%) are filtered out (no video needed).
   - Kill-switch concepts (REQUIRES_HUMAN_FALLBACK) are filtered out of the video queue
     and explicitly surfaced in human_intervention_concepts.
2. Target Duration Scaling (Bound to Concept Difficulty):
   - foundational: 30 seconds (±2s tolerance)
   - intermediate: 45 seconds (±3s tolerance)
   - advanced:     60 seconds (±3s tolerance)
3. Derives VideoTarget items:
   - concept_id: Graph ID (e.g. "CONCEPT_COARSE_ALIGNMENT")
   - concept_name: "Coarse Alignment"
   - definition: Factual description from source material
   - difficulty: "intermediate"
   - target_seconds: 45
   - directive: "Generate a 45-second AI video explaining Coarse Alignment"
   - chunk_ids: Source chunk IDs for visual illustration
   - page_start / page_end: Exact source pages
4. Sets Decision State:
   - "ALL_MASTERED": All concepts passed; video queue is empty.
   - "GENERATE_VIDEOS": Needs remediation; video queue contains targets.
   - "HUMAN_INTERVENTION": All failures hit kill switch; instructor alert required.
5. Saved to Disk:
   Path: storage/video_targets/<student_id>_<source_id>.json

6.5 STAGE 5: MEDIA MULTIPLEXING, WEBVTT SUBTITLES & VIDEO INDEXING
------------------------------------------------------------------
File: app/services/video_gen/muxer.py & app/services/video_gen/pipeline.py

1. Video Concatenation:

3. WebVTT Subtitle Generation:
   - Computes cue timestamps [00:00.000 --> 00:08.500] from measured scene durations.
   - Outputs formatted WebVTT subtitle track:
     Path: storage/runtime/videos/<video_id>/subtitles.vtt
4. Master Video Registry:
   - Registers completed metadata in the global index:
     Path: storage/runtime/videos/videos_index.json
   - Persists final job metadata:
     Path: storage/runtime/videos/<video_id>/job.json

6.6 STAGE 6: VIDEO STREAMING, CAPTIONS & STATUS API
---------------------------------------------------
File: app/api/video.py
1. GET /video/status/{job_id}: Returns live execution status, progress percentage (0-100%),
   and current stage message for polling UIs.
2. GET /video/{video_id}/stream: Streams the final_video.mp4 file via FastAPI FileResponse
   with media_type="video/mp4" supporting HTTP byte-range requests for smooth seeking.
3. GET /video/{video_id}/subtitles: Serves subtitles.vtt with media_type="text/vtt".
4. GET /video/list/{student_id}: Lists all available rendered remediation videos for a student.


================================================================================
7. STEP 3 -> STEP 4 HANDOFF INTERFACE & CONTRACTS
================================================================================
Once the student watches the remedial video lesson, the system transitions to Step 4
to verify that the conceptual weakness has been resolved.

HANDOFF CONTRACT:
1. Trigger Event: Video playback completion or learner initiates "Verify Mastery"
   from the video player modal.
2. Handoff Payload:
   - student_id: Identifier of the student
   - source_id: Source document ID
   - concept_id: Concept taught in the video
3. Verification Objective: Administer a short, highly focused 1-2 question re-test
   specifically testing comprehension of the concept just taught.
4. Isolation Guarantee: Re-test evaluates only the specific concept remediated;
   it does not re-test the entire curriculum.


================================================================================
8. STEP 4: REMEDIATION VERIFICATION & RE-TESTING LOOP (DATA FLOW & STORAGE)
================================================================================

Endpoints:
  - POST /remediation/start   (Generate targeted 1-2 question verification session)
  - POST /remediation/submit  (Grade verification answers, update profile, resolve target)
Files: app/api/remediation.py, app/services/remediation/engine.py

8.1 STAGE 1: VERIFICATION SESSION INITIALIZATION & PEDAGOGICAL VARIANTS
-----------------------------------------------------------------------
File: app/services/remediation/engine.py::create_remediation_session
1. Intake:
   - Receives student_id, source_id, concept_id, and question count (default: 1).
2. Concept Metadata Retrieval:
   - Loads KnowledgeGraph from storage/registry/<source_id>/knowledge_graph.json.
   - Extracts ConceptNode definitions, difficulty, and prerequisite connections.
3. Pedagogical Question Variants:
   Unlike initial diagnostic testing, verification questions use specialized variants:
   - "application": Presents a concrete scenario or calculation requiring the student
     to apply the principle learned in the video.
   - "misconception": Explicitly targets the common cognitive pitfall or distractor
     that caused the student to fail the initial assessment.
4. Generates fresh grounded question using generate_question_for_concept().
   - Fallback protection: If LLM is unavailable, generates deterministic verification question
     grounded in the concept's authoritative definition.
5. Snapshot & Session Creation:
   - Creates ConceptSnapshot for self-contained execution.
   - Assigns unique session_id: SESS_REM_<uuid4_hex>.
   - Persists session:
     Path: storage/assessment_sessions/<session_id>.json
     Status: READY

8.2 STAGE 2: GROUNDED QUESTION GENERATION & HIDDEN ANSWER KEY PROTECTION
------------------------------------------------------------------------
1. Strips hidden answer key (correct_index, explanation) to produce SafeQuestion objects.
2. Dispatches sanitized questions to the client via POST /remediation/start response:
   - session_id
   - student_id, source_id, concept_id
   - questions: List[SafeQuestion] (includes stem, 4 options, chunk_ids, page ranges)
   - status: "READY"

8.3 STAGE 3: VERIFICATION SUBMISSION GRADING & MASTERY STATE TRANSITION
-----------------------------------------------------------------------
File: app/services/remediation/engine.py::evaluate_remediation_submission
1. Intake:
   - Receives session_id, student_id, concept_id, and list of AnswerSubmissions.
2. Grading:
   - Compares student's selected_index against ground-truth correct_index in stored session.
   - Computes score, total, percentage, and detailed explanations.
   - Passing threshold: percentage >= 70.0%.
3. State Transition Logic (When Passed):
   - Concept mastery status transitions: "LEARNING" -> "MASTERED".
   - Increments correct_attempts and consecutive_correct count.
   - Updates StudentLearningProfile:
     * Adds concept to profile.strong_concepts and profile.strong_concept_ids.
     * Removes concept from profile.weak_concepts and profile.weak_concept_ids.
     * Recalculates average mastery score.
   - Saved to Disk:
     Path: storage/learning_profiles/<student_id>_<source_id>.json

8.4 STAGE 4: ANTI-LOOP KILL SWITCH ENFORCEMENT (>3 FAILURES)
------------------------------------------------------------
1. State Transition Logic (When Failed):
   - Increments attempts and resets consecutive_correct = 0.
   - Iteration Count Check:
     * If attempts > kill_switch_limit (default 3):
       Concept status is marked: "REQUIRES_HUMAN_FALLBACK".
       Anti-loop guardrail triggered: The automated video and testing loop is halted
       for this concept to prevent student frustration and cognitive exhaustion.
       Flagged for instructor intervention in the Instructor Portal.
     * Otherwise: Concept remains in "LEARNING" status.

8.5 STAGE 5: DYNAMIC VIDEO TARGET MATRIX RESOLUTION & PROFILE SYNC
------------------------------------------------------------------
File: app/services/remediation/engine.py & app/services/assessment/video_target.py
1. Resolving the Video Target:
   - When a concept is successfully verified as "MASTERED", the engine loads the
     VideoTargetMatrix from storage/video_targets/<student_id>_<source_id>.json.
   - Filters out the mastered concept from matrix.videos.
2. Dynamic Decision Update:
   - If matrix.videos is now empty:
     * If human_intervention_concepts is empty:
       decision = "ALL_MASTERED"
       summary = "All assessed concepts have been successfully mastered. No AI videos needed."
     * If human_intervention_concepts is not empty:
       decision = "HUMAN_INTERVENTION"
       summary = "Remaining items require human instructor intervention."
   - If matrix.videos still has remaining concepts:
     summary = "Remaining remediation targets: X concept(s)."
3. Persists updated VideoTargetMatrix to disk:
   Path: storage/video_targets/<student_id>_<source_id>.json
4. Closed Loop Completed:
   The remediation loop is officially closed. The student profile reflects verified
   mastery, and the video target queue automatically shrinks in real time.

11. END-TO-END DATA ENTITY LIFECYCLE & STATE TRANSITION MATRIX
================================================================================

ENTITY 1: SourceRecord (Step 1)
  UPLOADED ──► PROCESSING ──► EXTRACTING ──► NORMALIZING ──► INDEXING ──► VALIDATING ──► READY
                                                                               │
                                                                               └──► FAILED

ENTITY 2: AssessmentSession (Step 2 & Step 4)
  PLANNING ──► GENERATING ──► VALIDATING ──► READY ──► SUBMITTED ──► (EXPIRED after 24h)
                                                 │
                                                 └──► FAILED

ENTITY 3: ConceptMastery Status (Step 2 & Step 4)
  UNASSESSED
      │
      ▼ (First Assessment)
  LEARNING ─────────────── (Score >= 70% for 2 consecutive attempts) ──────────────► MASTERED
      │                                                                                  ▲
      │ (Failed attempt in Step 4 verification)                                         │
      ▼                                                                                  │
  LEARNING (attempts <= 3) ──► (Passed Step 4 verification) ─────────────────────────────┘
      │
      ▼ (Failed > 3 attempts)
  REQUIRES_HUMAN_FALLBACK ──► (Instructor reset via Portal) ──► LEARNING

ENTITY 4: VideoRenderJob (Step 3)
  PENDING ──► GENERATING_SCRIPT ──► SYNTHESIZING_VOICEOVER ──► RENDERING_VISUALS ──► MUXING_MEDIA ──► COMPLETED
                                                                                                 │
                                                                                                 └──► FAILED

ENTITY 5: VideoTargetMatrix Decision (Step 2 & Step 4)
  GENERATE_VIDEOS (1 or more unmastered concepts in video queue)
      │
      ▼ (Step 4 verification passes all concepts)
  ALL_MASTERED (0 concepts in video queue, 0 kill-switch concepts)
      │
      ▼ (All remaining failures hit kill switch >3 failures)
  HUMAN_INTERVENTION (0 concepts in video queue, >=1 in human_intervention_concepts)
