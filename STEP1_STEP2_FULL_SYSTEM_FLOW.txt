   FUNCTION: plan_assessment(kg, profile, max_questions, key_concepts)
   PURPOSE: Selects and orders concepts to test based on student mastery and conceptual hierarchy.
   INPUT: kg: KnowledgeGraph, profile: StudentLearningProfile, max_questions: int, key_concepts: list[str]
   PROCESSING:
     - Difficulty Classification via classify_difficulty(concept):
       * 0 prerequisites: "foundational"
       * 1-2 prerequisites: "intermediate"
       * >2 prerequisites: "advanced"

       * Tiers concepts: ~30% foundational, ~40% intermediate, ~30% advanced.
       * If key_concepts specified in Step 1 JSON, prioritizes matching nodes first.
     - If profile exists (Adaptive Re-Test):
       * Priority 1: Concepts in REQUIRES_HUMAN_FALLBACK (if not excluded)

       * Priority 3: Concepts in NOT_ATTEMPTED
       * Priority 4: Fill remaining from unselected
     - Prerequisite Pairing Rule (_apply_prerequisite_pairing):
       * Traverses DAG recursively.
       * For every advanced concept selected, guarantees all foundational prerequisite concepts are queued before it.
       * Implements visiting-set cycle detection to prevent infinite recursion on malformed graphs.

       * Verifies source_id matches allowed_source_id.
       * Verifies presence of provenance anchors (at least one of chunk_ids or content_ids).
       * Verifies page_start <= page_end and timestamp_start <= timestamp_end.
     - validate_grounding(question, context_text):
       * Extracts significant tokens (length >= 4, non-stopwords) from context and question.
       * Verifies word overlap >= 1; rejects hallucinated questions with zero source vocabulary overlap.
     - is_duplicate(new_question, existing_questions):
       * Computes Jaccard similarity of question stem tokens; rejects if > 0.8.
       * Rejects if >= 3 options match an existing question.
   OUTPUT: tuple[bool, str] (is_valid, error_reason)
   NEXT COMPONENT: Candidate accepted -> added to session.questions; rejected -> backfilled from reserve pool.

6. FILE: app/services/assessment/session_store.py
   FUNCTIONS: save_session(session), load_session(session_id)
   PURPOSE: File-based JSON persistence for AssessmentSession entities.
   STORAGE PATH: storage/assessment_sessions/{session_id}.json
   INPUT: AssessmentSession
   OUTPUT: Persisted file on disk or loaded Pydantic instance.
   NEXT COMPONENT: app/api/assessment.py::submit_assessment()

7. FILE: app/api/assessment.py & app/services/assessment/engine.py
   FUNCTION: submit_assessment(submission) -> grade_submission()
   PURPOSE: Grades submitted answers against hidden answer key, updates profile, detects prerequisite gaps, enforces kill switch.
   INPUT: submission: StudentSubmission (session_id, answers: list[AnswerSubmission])
   PROCESSING:
     - Loads session from disk; verifies status == "READY" (rejects with HTTP 409 if already submitted).
     - Checks session expiration (returns HTTP 410 Gone if datetime.now() > expires_at).
     - Validates answers: verifies question_ids belong to session; rejects duplicates with HTTP 400.
     - Reconstructs KnowledgeGraph: loads from disk registry OR reconstructs from session.concept_snapshot via reconstruct_kg_from_snapshot().
     - Hidden Answer Grading: compares answer.selected_index against question.correct_index.
     - Anti-Loop Kill Switch:
       * Increments iteration_count for each failed concept.
       * If iteration_count > settings.kill_switch_limit (default 3), status is set to "REQUIRES_HUMAN_FALLBACK".
       * Concept is permanently locked out of automated video queues.
     - False-Mastery Protection:
       * Requires correct_attempts >= settings.mastery_threshold (default 2) AND consecutive_correct >= 1 to reach "MASTERED".
     - Prerequisite Gap Detection:
       * If student fails child concept AND fails its prerequisite concept, records explicit gap description:
         "Prerequisite gap: Failed '<child>' (child) AND '<parent>' (parent)".
     - Updates StudentLearningProfile: recalculates overall_score, strong/weak concept IDs, and masteries.
     - Calls build_video_target_matrix() and save_video_matrix().
     - Updates session.status to "SUBMITTED".
   OUTPUT: Graded result JSON (score, total, percentage, results, prerequisite_gaps, profile_summary, concept_scores, video_target_matrix).
   NEXT COMPONENT: app/services/assessment/video_target.py

8. FILE: app/services/assessment/video_target.py
   FUNCTION: build_video_target_matrix(profile, kg, source_filename, pass_threshold, session)
   PURPOSE: Compiles the authoritative Step 3 Video Target Matrix blueprint.
   INPUT: profile: StudentLearningProfile, kg: KnowledgeGraph, source_filename: str, pass_threshold: float = 70.0, session: AssessmentSession
   PROCESSING:
     - Scans concept masteries on profile:
       * Filters out concepts with status == "MASTERED" or last_score >= 70.0 (no video required).
       * Filters out concepts with status == "REQUIRES_HUMAN_FALLBACK" (routes to human_intervention_concepts).
       * Isolates failed concepts needing automated remediation.
     - Duration Scaling by Conceptual Depth (classify_difficulty):
       * Foundational concept: 30 seconds
       * Intermediate concept: 45 seconds
       * Advanced concept:     60 seconds
     - Recovers visual provenance from session questions: chunk_ids, source_content_ids, page ranges.
     - Formats explicit directives:
       e.g. "Generate a 45-second AI video explaining Newton's Second Law".
     - Evaluates Decision State:
       * "ALL_MASTERED": 0 videos needed, 0 human intervention concepts.
       * "GENERATE_VIDEOS": 1+ videos in queue.
       * "HUMAN_INTERVENTION": 0 videos in queue, but 1+ concepts hit kill switch.
       * Mixed State: decision="GENERATE_VIDEOS" with human intervention notice appended to summary.
     - Saves matrix to storage/video_targets/{student_id}_{source_id}.json via save_video_matrix().
   OUTPUT: VideoTargetMatrix Pydantic model.
   NEXT COMPONENT: Step 3 AI Video Generation Engine (consumed via filesystem or GET /assessment/video-target/{student_id}/{source_id}).

--------------------------------------------------------------------------------
1. VECTOR DATABASE: QDRANT COLLECTION SPECIFICATION
--------------------------------------------------------------------------------
COLLECTION NAME: visualai_layer_a
DISTANCE METRIC: Cosine (qmodels.Distance.COSINE)
VECTOR DIMENSION: Dynamic probe via gemini-embedding-2 (typically 768 dimensions)
POINT ID GENERATION:
  Deterministic UUIDv5 calculated as:
  uuid.uuid5(uuid.NAMESPACE_DNS, f"{chunk.source_id}::{chunk.chunk_id}::{chunk.text[:100]}")
  Guarantee: Upserting identical chunks updates existing vector points in-place without duplicating records.

QDRANT PAYLOAD SCHEMA (RichChunk):
┌───────────────────────────┬──────────────┬─────────────────────────────────────────────────────────────┐
│ Field Name                │ Type         │ Description / Purpose                                       │
├───────────────────────────┼──────────────┼─────────────────────────────────────────────────────────────┤
│ chunk_id                  │ String       │ Unique chunk identifier (e.g. "CHUNK_f6366421aaae")         │
│ source_id                 │ String       │ Source document identifier (e.g. "SRC_63d54087dc2e")         │
│ asset_id                  │ String       │ Asset identifier (e.g. "AST_c9e1b20e3a93")                  │
│ layer                     │ String (Enum)│ Always "A" (authoritative source ground truth)              │
│ type                      │ String       │ Always "rich_chunk"                                         │
│ text                      │ String       │ Extracted text chunk content (~500-1000 tokens)             │
│ modality                  │ String (Enum)│ "pdf" | "image" | "txt" | "video"                           │
│ chapter                   │ String | null│ Chapter title detected by structurer                        │
│ section                   │ String | null│ Section title detected by structurer                        │
│ concept_ids               │ List[String] │ Concept IDs mapped to this text chunk                       │

2. INPUT:
   AssessmentStartRequest (student_id, source_id, max_questions, optional step1_output)

3. VALIDATION & INTEGRITY:
   - Sanitizes student_id and source_id (ignores Swagger "string" placeholders)
   - Verifies session integrity (source_id in URL matches source_id in Step 1 payload)
   - Verifies source exists in storage/registry/sources_index.json and status == "READY" (HTTP 423 if indexing)

4. CALLS:
   app/services/registry.py::load_knowledge_graph(source_id)
   (or extracts in-memory graph from payload if present)

5. CALLS:
   app/services/assessment/profile.py
   get_or_create_profile(student_id, source_id)
   - Reads storage/learning_profiles/{student_id}_{source_id}.json or creates fresh instance

6. CALLS:
   app/services/assessment/planner.py
   plan_assessment(kg, profile, max_questions, key_concepts)
   - Identifies kill-switch concepts to strictly exclude
   - Classifies concept difficulty (0 prereqs = foundational, 1-2 = intermediate, >2 = advanced)
   - If cold start: samples balanced ratio (~30% foundational, ~40% intermediate, ~30% advanced)
   - If existing profile: prioritizes LEARNING and NOT_ATTEMPTED concepts
   - Applies Prerequisite Pairing Rule (recursively queues foundational concepts before advanced dependents)
   - Builds primary candidate queue and reserve pool

7. CALLS:
   ConceptSnapshot serializing:
   Builds ConceptSnapshot dictionary embedded directly into AssessmentSession

8. SESSION CREATION:
   Creates AssessmentSession(session_id, student_id, source_id, status="GENERATING", expires_at=now+24h)

9. CALLS:
   app/services/assessment/generator.py
   generate_question(concept, source_id, difficulty, provided_chunks, max_retries, provider)
   - Queries Qdrant visualai_layer_a scoped strictly to source_id & layer="A"
   - Generates question with provider (Gemini / Ollama / Mock) or falls back to deterministic grounded generator

10. CALLS:
    app/services/assessment/validator.py
    validate_question() -> checks structure and provenance anchors
    validate_grounding() -> checks vocabulary overlap with source text
    is_duplicate() -> checks Jaccard similarity against existing questions
    - On failure: logs rejection and immediately pulls next candidate from reserve pool (backfilling)!

11. CALLS:
    app/services/assessment/session_store.py
    save_session(session)
    - Persists complete session to storage/assessment_sessions/{session_id}.json

12. TRANSFORMATION:
    Sanitizes questions into SafeQuestion objects:
    - Strips correct_index, correct answer text, and explanation
    - Retains chunk_ids, page ranges, and timestamps for student verification

13. OUTPUT:
    HTTP 200 JSON dictionary with session_id, expires_at, question_count, questions: list[SafeQuestion], shortfall.

--------------------------------------------------------------------------------
FLOW #3 — STEP 2 SUBMISSION, GRADING & VIDEO TARGET MATRIX WORKFLOW
--------------------------------------------------------------------------------

1. ENTRY:
   app/api/assessment.py
   submit_assessment(submission)

2. INPUT:
   StudentSubmission(session_id, answers: list[AnswerSubmission(question_id, selected_index)])

3. CALLS:
   app/services/assessment/session_store.py
   load_session(session_id)
   - Rejects with HTTP 404 if session missing
   - Rejects with HTTP 409 if session.status == "SUBMITTED"
   - Rejects with HTTP 400 if session.status != "READY"

4. VALIDATION:
   - Checks session expiration (returns HTTP 410 Gone if datetime.now() > expires_at)
   - Verifies question_ids belong to session; rejects duplicate answers with HTTP 400

5. KNOWLEDGE GRAPH RESOLUTION:
   - Loads KnowledgeGraph from storage/registry/{source_id}/knowledge_graph.json
   - Fallback (Phase 2B): Reconstructs minimal graph from session.concept_snapshot via reconstruct_kg_from_snapshot()

6. CALLS:
   app/services/assessment/profile.py
   get_or_create_profile(session.student_id, session.source_id)

7. CALLS:
   app/services/assessment/engine.py
   grade_submission(submission, session, kg, profile)
   - Compares selected_index against ground-truth correct_index
   - Computes overall score and percentage
   - Updates concept mastery:
     * Increments attempts
     * If all correct: increments correct_attempts, consecutive_correct
     * If incorrect: resets consecutive_correct to 0, increments iteration_count
     * False-Mastery Guard: requires correct_attempts >= 2 for "MASTERED"
     * Anti-Loop Kill Switch: if iteration_count > 3, sets status to "REQUIRES_HUMAN_FALLBACK"
   - Prerequisite Gap Detection:
     * If child concept failed AND parent concept failed, appends gap description
   - Updates profile aggregate scores and lists

8. CALLS:
   app/services/assessment/session_store.py
   session.status = "SUBMITTED"
   save_session(session)

9. CALLS:
   app/services/assessment/profile.py
   save_profile(profile)
   - Persists to storage/learning_profiles/{student_id}_{source_id}.json

10. CALLS:
    app/services/assessment/video_target.py
    build_video_target_matrix(profile, kg, source_filename, session)
    - Filters out mastered/passed concepts (score >= 70%)
    - Filters out kill-switch concepts (surfaced in human_intervention_concepts)
    - Isolates unmastered concepts
    - Scales target duration: Foundational = 30s, Intermediate = 45s, Advanced = 60s
    - Attaches provenance chunk_ids and page numbers from session questions
    - Sets decision state: "ALL_MASTERED" | "GENERATE_VIDEOS" | "HUMAN_INTERVENTION"

11. CALLS:
    app/services/assessment/video_target.py
    save_video_matrix(video_matrix)
    - Persists to storage/video_targets/{student_id}_{source_id}.json

12. OUTPUT:
    HTTP 200 JSON dictionary with score, percentage, results, prerequisite_gaps, profile_summary, concept_scores, and video_target_matrix.

PHASE 9 — AI / LLM / VISION PROCESSING FLOW
================================================================================

The system contains four distinct AI processing stages:

--------------------------------------------------------------------------------
STAGE 1: DIAGRAM & KEYFRAME VISION ANALYSIS
--------------------------------------------------------------------------------
- Models Used: Google Gemini API (gemini-3.5-flash)
- Implementation File: app/services/vision.py
- Functions: describe_image(), describe_frame(), describe_image_file()
- Diagram Prompt (_DIAGRAM_PROMPT):
  "You are an expert textbook diagram and image reader with perfect visual recognition...
   1. Transcribe ALL text exactly as written...
   2. Describe ALL visual elements (shapes, arrows, lines)...
   3. Explain the flow, process, or concept...
   4. Output ONLY the description."
- Frame Prompt (_FRAME_PROMPT):
  "You are an expert lecture frame analyzer with perfect visual recognition...
   1. Transcribe ALL text visible (whiteboard, slides)...
   2. Describe diagrams and visual aids...
   3. Describe speaker actions if relevant...
   5. If frame shows only speaker: 'Speaker visible, no board/slide content.'"
- Media Serialization: Base64-encoded bytes with mime_type="image/png" or "image/jpeg".
- Fallback: Returns placeholder text if vision API returns empty string.

--------------------------------------------------------------------------------
STAGE 2: CURRICULUM & KNOWLEDGE GRAPH EXTRACTION
--------------------------------------------------------------------------------
- Model Used: Google Gemini API (gemini-3.5-flash)
- Implementation File: app/services/structurer.py
- Function: process_structure_and_concepts()
- Prompt (_STRUCTURE_AND_CONCEPT_PROMPT):
  Demands STRICT JSON containing topic_name, difficulty_level, chapters, sections, concepts, definitions, prerequisite_concept_ids, source_content_ids.
- Grounded Regex Heuristic Fallback (_fallback_outputs):
  * Activated when: Gemini hits HTTP 429 quota exhaustion or network timeout.
  * Operation: Parses capitalized acronyms (e.g. "FSOC"), definition triggers ("X is defined as...", "X refers to..."), and heading patterns.
  * Guarantee: KnowledgeGraph and TopicBlueprint are NEVER empty.

--------------------------------------------------------------------------------
STAGE 3: DENSE VECTOR EMBEDDINGS
--------------------------------------------------------------------------------
- Model Used: Google Gemini Embeddings (models/gemini-embedding-2)
- Implementation File: app/db/vector_store.py
- Function: _embed()
- Task Type: task_type="retrieval_document"
- Dimensions: 768 dimensions (probed dynamically on initialization)
- Upsert Target: Qdrant collection visualai_layer_a

--------------------------------------------------------------------------------
STAGE 4: GROUNDED ASSESSMENT QUESTION GENERATION
--------------------------------------------------------------------------------
- Provider Abstraction: app/services/assessment/providers.py
  * GeminiProvider: gemini-3.5-flash (cloud)
  * OllamaProvider: llama3.2 (local HTTP http://localhost:11434/api/generate)
  * MockProvider: deterministic offline JSON generator for unit testing
- Factory: get_default_provider() resolved via settings.llm_provider
- Generator Implementation: app/services/assessment/generator.py::generate_question()
- Prompt Strategy (_QUESTION_PROMPT):
  * Injects exact authoritative chunk text retrieved from Qdrant Layer A.
  * Negative Prompt: "Based ONLY on this text, generate a multiple-choice question. Provide exactly 1 correct answer and 3 plausible but factually incorrect options. Do not use trivial or obviously silly distractors."
- Deterministic Grounded Fallback (_generate_grounded_fallback):
  * Activated when: LLM provider throws quota error (429), network error, or invalid JSON.
  * Correct Index Variation: MD5 hash of concept_id modulo 4 deterministically distributes correct answers across [0, 1, 2, 3] (prevents predictable option 0 bias).
  * Distractors: Synthesized from concept domain and prerequisite relationships.

PHASE 10 — STEP 1 -> STEP 2 CONNECTION CONTRACT
================================================================================

The connection between Step 1 and Step 2 is explicit, deterministic, and contractual.

EXPLICIT ARCHITECTURAL QUESTIONS & ANSWERS:

1. WHAT DOES STEP 1 PRODUCE?
   - A registered SourceRecord (with unique source_id e.g. "SRC_63d54087dc2e", status: "READY").
   - Preserved original study file at storage/uploads/{source_id}/original.{ext}.
   - Normalized ContentUnit records at storage/registry/{source_id}/content_units.json.
   - Conceptual KnowledgeGraph and TopicBlueprint at storage/registry/{source_id}/knowledge_graph.json.
   - Vectorized RichChunks in Qdrant collection visualai_layer_a with layer="A", concept_ids, and content_ids.

2. WHERE IS IT STORED?
   - File system: storage/registry/{source_id}/
   - Vector DB: Qdrant collection visualai_layer_a (tagged with payload field "source_id")

3. HOW DOES STEP 2 FIND IT?
   - The client passes the source_id from Step 1's response to Step 2 endpoints:
     POST /assessment/start { "student_id": "student_1", "source_id": "SRC_63d54087dc2e" }
   - Or automatically via single-step handoff:
     POST /upload?auto_start_assessment=true&student_id=student_1

4. WHICH EXACT FILE READS IT?
   - app/api/assessment.py (lines 120-136)
   - app/services/registry.py (load_knowledge_graph, get_source_record)
   - app/services/assessment/generator.py (search_concept_chunks)

5. WHICH EXACT FUNCTIONS PROCESS IT?
   - app/api/assessment.py::start_assessment()
   - app/services/registry.py::load_knowledge_graph()
   - app/services/assessment/planner.py::plan_assessment()
   - app/services/assessment/generator.py::search_concept_chunks()

6. WHAT DATABASE RECORDS CONNECT STEP 1 AND STEP 2?
   - source_id: Foreign key string matching across:
     * sources_index.json::source_id
     * knowledge_graph.json
     * Qdrant payload::source_id
     * AssessmentSession::source_id
     * StudentLearningProfile::source_id
     * VideoTargetMatrix::source_id

7. WHAT HAPPENS IF STEP 1 DATA IS MISSING?
   - If source_id is not in sources_index.json and no knowledge graph is in payload:
     Returns HTTP 404 Not Found: "Source '<source_id>' not found in registry".
   - If source status is not "READY" (e.g. still "INDEXING"):
     Returns HTTP 423 Locked: "Source '<source_id>' is not ready (status: INDEXING). Wait for ingestion."
   - If knowledge graph is empty:
     Returns HTTP 422 Unprocessable Entity: "No concepts found for source. Knowledge graph is empty."
   - Offline Snapshot Resilience (Phase 2B):
     If grading a submission and storage/registry/{source_id}/knowledge_graph.json was deleted,
     reconstruct_kg_from_snapshot() reconstructs the graph from session.concept_snapshot!

8. WHAT HAPPENS IF STEP 2 FAILS?
   - If question generation produces 0 valid questions:
     session.status is marked "FAILED", saved to disk, and API returns HTTP 422 Unprocessable Entity.
   - If submission grading fails:
     Returns HTTP 400 (if invalid question IDs) or HTTP 410 (if expired) or HTTP 409 (if already submitted).
   - Step 1 registry and vector chunks remain completely intact and unaffected.

9. IS THE CONNECTION SYNCHRONOUS OR ASYNCHRONOUS?
   - Synchronous HTTP request-response cycle. POST /assessment/start executes planning, vector search, question generation, and validation before returning the sanitized quiz JSON to the caller.

10. IS ANYTHING CURRENTLY MOCKED OR BYPASSED?
    - Production runtime defaults to real Google Gemini API and real Qdrant.
    - MockProvider exists in app/services/assessment/providers.py for zero-cost offline test environments.
    - Embedded local Qdrant exists as an automatic fallback when Docker Qdrant is offline.
    - Regex heuristic structurer exists as an automatic fallback when Gemini hits rate limits (HTTP 429).
    - Grounded template generator exists as an automatic fallback when LLM question generation fails.

PHASE 14 — ERROR AND FAILURE FLOW
================================================================================

1. INVALID INPUT / DISGUISED FILE:
   - Detected in: app/services/registry.py::validate_file()
   - Mechanism: Checks file extension against ALLOWED_EXTENSIONS; verifies magic bytes.
   - Result: Raises ValueError.
   - API Effect: HTTP 400 Bad Request ("File signature check failed...").
   - User Experience: Error banner in Web Dashboard explaining file is unsupported or corrupted.

2. EMPTY CONTENT FILE:
   - Detected in: app/api/upload.py (line 93)
   - Mechanism: Checks if extraction_result.units is empty.
   - Result: update_source_status(source_id, "FAILED", error_message="No content extracted").
   - API Effect: HTTP 422 Unprocessable Entity.

3. GEMINI API QUOTA EXHAUSTION (HTTP 429 RATE LIMIT):
   - In Step 1 Structurer (app/services/structurer.py):
     Catches exception and immediately invokes _fallback_outputs().
     Regex heuristic parser extracts acronyms, definitions, and headings directly from text blocks.
     Pipeline NEVER crashes; KnowledgeGraph is guaranteed non-empty.
   - In Step 2 Question Generator (app/services/assessment/generator.py):
     Detects "exceeded your current quota" or "429"; switches to _generate_grounded_fallback().
     Builds deterministic questions using MD5 hash modulo 4 for answer indices and prerequisite distractors.

4. QDRANT VECTOR STORE OUTAGE:
   - During Connection:
     get_client() in app/db/vector_store.py probes Docker at http://localhost:6333 (timeout: 2s).
     If unreachable, logs info and immediately falls back to embedded on-disk Qdrant storage at storage/qdrant/.
   - During Upsert:
     If Qdrant fails completely, upsert_safely() raises HTTPException(status_code=503, detail="Layer A vector sync failed...").

5. FFMPEG NOT INSTALLED ON HOST:
   - Detected in: app/services/video/av_splitter.py::_find_ffmpeg()
   - Mechanism: extract_audio() catches missing binary.
   - Fallback: app/services/video/pipeline.py catches error and falls back to _visuals_only_units(),
     extracting visual keyframes without audio rather than failing the whole upload.

6. QUESTION GENERATION REJECTION / HALLUCINATION DETECTED:
   - Detected in: app/services/assessment/validator.py (validate_question, validate_grounding, is_duplicate)
   - Recovery: Rejected candidate is logged; generator immediately backfills by pulling the next concept from the reserve pool.
   - User Effect: Student receives full target question count without noticing internal retries.

7. EXPIRED ASSESSMENT SESSION:
   - Detected in: app/services/assessment/engine.py (lines 71-75)
   - Condition: datetime.now(timezone.utc) > datetime.fromisoformat(session.expires_at)
   - Result: Raises ValueError("Assessment session has expired...").
   - API Effect: HTTP 410 Gone.
   - User Experience: Dashboard alerts student that quiz time limit elapsed; prompts starting a new quiz.

8. DUPLICATE QUESTION SUBMISSION:
   - Detected in: app/api/assessment.py (lines 382-405)
   - Condition: session.status == "SUBMITTED" or duplicate question_id in answers list.
   - API Effect: HTTP 409 Conflict (already submitted) or HTTP 400 Bad Request (duplicate question ID).

9. DISK REGISTRY UNAVAILABILITY DURING GRADING:
   - Detected in: app/api/assessment.py (lines 408-426)
   - Condition: storage/registry/{source_id}/knowledge_graph.json is missing or inaccessible.
   - Recovery (Phase 2B): reconstruct_kg_from_snapshot() reconstructs KnowledgeGraph directly
     from session.concept_snapshot saved in the session JSON file.
   - User Effect: Grading succeeds seamlessly without disk dependency.

10. ANTI-LOOP KILL SWITCH (>3 REPEATED FAILURES):
    - Detected in: app/services/assessment/engine.py (lines 135-138)
    - Condition: mastery.iteration_count > settings.kill_switch_limit (default 3)
    - Mechanism: Sets mastery.status = "REQUIRES_HUMAN_FALLBACK".
    - Effect:
      * Concept is permanently excluded from future automated quiz planning.
      * Concept is filtered out of VideoTargetMatrix automated video queues.
      * Concept is surfaced in human_intervention_concepts for teacher/instructor intervention.

BOX-BY-BOX ARCHITECTURAL SUMMARY:
1. [ENTRY]: app/api/upload.py receives multipart file streams, enforces file size limits (<500MB), and verifies magic byte signatures.
2. [STEP 1]: Dispatcher routes file to PyMuPDF, Gemini Vision, or FFmpeg/Whisper/OpenCV; structurer generates hierarchical KnowledgeGraph; chunker maps Layer A provenance.
3. [DATABASE/STORAGE]: Qdrant stores dense embeddings with deterministic UUIDv5 IDs; disk registry stores immutable source files, ContentUnits, and KnowledgeGraph JSONs.
4. [STEP 1 OUTPUT]: Contractual handoff point: source_id string referencing a verified READY study document with extracted concepts.
5. [STEP 2]: Assessment planner applies cold-start balance and prerequisite pairing; generator pulls chunks from Qdrant and authors MCQs; validator gates grounding and backfills from reserve candidates; dispatches safe questions.
6. [PROCESSING]: Grading engine compares answers with backend key, prevents lucky guesses, halts infinite failure loops via kill switch, and pinpoints root prerequisite gaps.
7. [DATABASE/STORAGE]: Active sessions, cumulative student profiles, and remedial video blueprints are persisted as atomic structured JSON documents on disk.
8. [FINAL OUTPUT]: VideoTargetMatrix blueprint specifying target seconds (30s/45s/60s), visual chunk provenance, and teacher alerts for upcoming Step 3 automated video generation.
